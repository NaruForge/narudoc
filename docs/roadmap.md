# NaruDoc 장기 로드맵

이 문서는 NaruDoc이 궁극적인 제품 경험에 도달하기 위해 갖춰야 할 능력과 발전 순서를 설명한다. 기능 구현 명세, 작업 대장, 출시 일정 또는 현재 지원 기능 목록이 아니다.

제품의 목적과 불변 원칙은 [제품 비전](product.md)이 소유한다. 이 로드맵에 항목이 있다는 사실은 구현 승인이나 출시 약속을 뜻하지 않는다.

## 문서의 역할과 사용법

| 현재 구현·파일 문법·입출력 계약 | [아키텍처](architecture.md), [파일 문법](format.md), [CLI](cli.md) |

단계 번호는 발전 방향을 설명하기 위한 이름이지 버전, 일정 또는 전면적인 착수 제한이 아니다. 필요한 선행 능력이 검증되면 서로 다른 단계의 작업을 병행할 수 있다. 실제 작업의 순서와 승인은 Issue에서 결정한다.

현재 단계, 완료 체크박스, 진행률, 담당자, Issue별 상태를 이 문서에 복제하지 않는다. 달성 여부와 검증 근거는 실제 작업 기록에서 확인한다.

## 완성형에서 기대하는 경험

작성자는 문법이나 내부 ID/index를 몰라도 기술문서를 시각적으로 작성한다. Agent와 자동화는 같은 문서 규칙으로 필요한 내용을 조회·편집·검증·출력한다. 작성자와 검토자는 원문 및 변경 결과를 전용 편집기 없이 읽을 수 있다.

대표 사용 흐름은 다음과 같다.

- 설계서를 작성하고 표·그림·수식·각주와 상호참조를 넣는다. 객체의 순서가 바뀌면 표시 번호와 참조가 일관되게 갱신된다.
- Agent에게 특정 문장이나 셀의 수정을 맡긴다. 변경 범위와 진단을 확인하고 무관한 원문이 유지됐는지 검토한다.
- 여러 문서와 자산을 하나의 기술문서 묶음으로 구성하고, 참조를 검증한 뒤 배포 가능한 결과물을 만든다.

[SDoc 기능 안내서](https://github.com/NaruForge/sdoc-editor/blob/main/docs/MANUAL.md)는 실제 기술문서 작업의 참고 자료다. SDoc의 기능·저장 형식·VS Code 결합 구조를 그대로 복제하는 것을 목표로 삼지 않는다.

## 발전 단계 개요

| 단계 | 도달하려는 사용자 결과 |
| --- | --- |
| R0. 공통 엔진과 신뢰 가능한 변경 | 사람과 Agent의 변경을 같은 규칙으로 검증하고 원본을 보호한다. |
| R1. 자연스러운 단일 문서 편집 | 내부 명령이나 위치 번호 없이 본문에서 직접 문서를 작성한다. |
| R2. 기술문서 표현과 공통 의미 체계 | 표·그림·수식·캡션·번호·참조를 갖춘 기술문서를 작성한다. |
| R3. 여러 문서와 Book 구성 | 파일·자산·장 순서·참조 범위를 관리하며 문서 묶음을 유지한다. |
| R4. 재현 가능한 출판 | 원본을 바꾸지 않고 단일 문서와 Book의 결과물을 생성한다. |
| R5. 도입 편의와 상호운용 | 템플릿·변환·패키지·외부 연결로 실제 사용 비용을 낮춘다. |

기능은 가능한 한 작은 종단 사용 흐름으로 완성한다. 모델만 모두 만든 뒤 GUI를 붙이거나, GUI에서만 구현한 의미 규칙을 나중에 엔진으로 옮기는 방식은 피한다.

## R0. 공통 엔진과 신뢰 가능한 변경

**목표:** 편집기·호스트와 무관하게 문서 변경을 계획하고 검증할 수 있다.

주요 능력은 원본 보존 파싱·의미 편집·참조 검증, 공통 입력 계약, 대상 식별, 순차 편집, 충돌 감지, 안전한 저장이다. CLI의 도움말·기능 발견·구조화된 오류와 개발 지침·계약·테스트의 탐색 경로도 포함한다.

**달성 기준**

- 동일한 의미 변경이 CLI/API와 해당 GUI 경로에서 일관된 결과를 낸다. 핵심 문서 작업은 GUI 실행을 요구하지 않는다.
- No-op은 원본 bytes를 유지하고, 국소 편집은 대상과 필요한 문법 경계만 변경한다. 잘못된 입력·충돌·후속 작업 실패는 정해진 저장 계약에 따라 처리한다.
- 새 기능의 입력·대상·검증 규칙을 여러 클라이언트에 다시 작성하지 않는다. 계약 불일치와 모듈 경계 위반은 검증에서 드러난다.

이 능력은 이후 단계에서도 계속 유지한다. 기반 정비 자체를 끝없는 선행 프로젝트로 확대하지 않는다.

## R1. 자연스러운 단일 문서 편집

**목표:** 작성자가 본문에 커서를 놓고 일반적인 문서 편집 동작으로 내용을 작성한다.

주요 능력은 문서 전체의 선택·커서 이동, Enter/Backspace에 의한 문단 분리·병합, 복사·잘라내기·여러 문단 붙여넣기, 사용자 의도 단위의 undo/redo다. 제목·문단·목록·링크·코드와 기본 인라인 서식을 직접 편집한다.

새 객체의 내부 식별자와 삽입 위치는 시스템이 처리한다. 명시적인 요구사항 번호처럼 사용자가 관리할 가치가 있는 정보만 적절한 속성 UI에 드러낸다. 특정 메뉴 형태나 편집기 라이브러리는 이 문서에서 확정하지 않는다.

**달성 기준**

- 일반 본문 작성에 `paragraph index`, inline path 또는 ID 입력 폼이 필요하지 않다. 빈 입력과 조합 중인 한글을 자연스럽게 다룬다.
- 문단을 넘는 편집과 undo/redo에서 내용·서식·선택이 일관되며, 저장 후의 undo와 외부 변경 충돌 정책도 명확하다.
- 미지원 객체를 조용히 삭제하거나 평탄화하지 않는다. 실제 대상 OS의 한글 IME, 기본 키보드 접근성, 저장·재열기 경험을 확인한다.

문서 단위 편집과 원본 매핑의 책임을 먼저 검증한다. 폼과 단축키를 계속 추가하는 것으로 이 단계를 대체하지 않는다.

## R2. 기술문서 표현과 공통 의미 체계

**목표:** 설계서와 기술보고서의 내용을 별도 문자열 조작 없이 표현·편집·검증한다.

| 능력 | 목표 범위 |
| --- | --- |
| 본문 구조 | 중첩 목록, 인용문, callout, 기술적 표기에 필요한 위·아래 첨자 등 기본 표현 |
| 표 | 셀 편집, 행·열 추가/삭제, 머리글, 캡션과 참조 대상 지정 |
| 자산과 그림 | 문서 기준 자산 경로, 이미지 삽입·교체·붙여넣기, 캡션·대체 텍스트, 누락·위험 경로 진단 |
| 수식 | 편집 가능한 텍스트 원문의 인라인/블록 수식, 미리보기, 필요한 경우 번호와 참조 |
| 공통 참조 | 안정적인 대상 식별, 캡션/라벨, 번호 정책, 의미 기반 상호참조 |
| 각주 | 본문 참조와 정의, 번호·이동·미정의/미사용 진단 정책 |
| 문서 정보 | 제목·작성자·문서 버전·언어 등 명시적인 metadata |

객체 식별, 캡션, 표시 번호는 서로 다른 개념이다. 모든 객체에 캡션이나 번호를 강제하지 않는다. 번호와 참조 표시가 바뀔 때 관련 없는 원문까지 다시 쓰지 않는 방향을 따른다.

그림·표·수식에 번호와 참조 로직을 각각 복제하지 않는다. 공통 규칙의 경계를 먼저 정하되, 미래의 모든 객체를 포괄하는 프레임워크를 먼저 만들지 말고 실제 객체의 종단 흐름으로 검증한다.

**달성 기준**

- 파라미터 표, 그림, 수식, 각주와 참조가 있는 공개 가상 설계서를 작성·수정·재열기 할 수 있다. 해당 의미 변경은 headless 경로로도 수행한다.
- 객체를 삽입하거나 순서를 바꿔도 참조가 다른 대상을 가리키지 않는다. 표시 번호·라벨은 같은 정책에서 계산되고 깨진 참조는 진단된다.
- 자산을 포함한 문서를 정해진 기준 경로와 함께 옮길 수 있다. 생성 metadata나 수정 시각 때문에 no-op 원본이 달라지지 않는다.

병합 셀, 복잡한 표 레이아웃, 풍부한 색상·장식은 기본 구조와 참조보다 후순위다. Requirement는 우선 generic directive를 활용하며, 전용 상태 전이·추적성 검증은 실제 도메인 요구가 확인될 때 별도로 검토한다.

## R3. 여러 문서와 Book 구성

**목표:** 파일과 자산으로 분리된 기술문서를 유지하고 필요한 순서로 묶는다.

문서 묶음은 작업 대상 파일·자산·해석 범위를 정하고, Book은 출판할 문서의 선택·장 순서·출력 범위를 정한다. 두 개념을 구분하되 별도의 복잡한 관리 플랫폼을 전제하지 않는다.

주요 능력은 문서 간 참조, 자산 해석, ID 유효 범위, 문서 이동·이름 변경의 영향 분석, 묶음 전체 검증, 통합 목차, 번호 범위와 Book 구성이다. 필요할 경우 읽을 수 있는 구성 파일을 사용하며 구체적 형식은 별도 설계에서 결정한다.

**달성 기준**

- 여러 문서를 장 순서대로 조합하고 전체 목차·번호·참조를 같은 해석 규칙으로 검증한다.
- 같은 로컬 ID가 다른 문서에 있는 경우와 파일 이동을 모호하게 처리하지 않는다. 변경 대상과 영향 범위를 확인할 수 있다.
- 묶음이 없어도 구성 문서의 원문을 읽고 제한을 이해할 수 있다. 각주·자산 등의 합성 한계는 진단하며 조용히 누락하지 않는다.

다중 문서 지원이 자동으로 다중 파일 transaction이나 실시간 공동 편집을 의미하지는 않는다. 그 보장 범위는 별도 요구와 검증으로 결정한다.

## R4. 재현 가능한 출판

**목표:** 편집 원본을 유지하면서 읽고 배포할 수 있는 결과물을 만든다.

HTML과 PDF를 우선하며, 호환성 수요에 따라 Markdown/AsciiDoc을 검토한다. 문서 내용, 공유할 출판 설정, 사용자별 화면 설정을 구분한다. 번호·캡션·참조의 의미는 출력 경로가 달라도 같아야 한다.

**달성 기준**

- 단일 문서 및 준비된 Book을 같은 문서 의미에 따라 출력하고, 외부 자산 포함 방식과 결과물의 이동성을 설명할 수 있다.
- 글꼴·renderer·설정 차이를 포함한 재현 조건이 명확하다. 같은 입력과 고정한 조건에서 구조·번호·참조가 일관된다.
- 실패·취소·기존 출력 충돌을 처리하고 원본을 수정하지 않는다. 변환에서 표현할 수 없는 내용은 손실 또는 제한으로 표시한다.

단일 문서 HTML/PDF는 R3 전체 완료를 기다릴 필요가 없다. Book 출력에 필요한 문서 합성과 참조 범위만 실제 선행 조건으로 둔다. 정교한 출판용 페이지 배치나 Word 전체 기능 복제는 목표가 아니다.

## R5. 도입 편의와 상호운용

**목표:** 사용자가 익숙한 자료와 환경에서 NaruDoc을 실제로 사용할 수 있다.

주요 후보는 문서/팀 템플릿, Markdown·HTML 가져오기, SDoc 이행, 소스 기반 다이어그램, 설치 가능한 CLI·편집기 패키지, 공개 SDK와 호스트 통합이다. 템플릿·기본 설치 경로처럼 독립적인 항목은 앞 단계부터 제공할 수 있다.

**달성 기준**

- 새 사용자가 설치·예제·help만으로 첫 문서를 만들고 저장·검증·출력을 수행한다. 개발 저장소 내부를 이해해야만 사용할 수 있는 상태를 벗어난다.
- 가져오기와 이행은 지원 범위·손실·원본 보존을 명시하며 조용한 변환을 피한다. 실패 시 기존 원본을 복구할 수 있다.
- 다이어그램은 renderer가 없어도 원문을 보존한다. 네트워크 전송은 명시적 권한 정책 아래에서만 수행한다.
- 공개 API의 안정성·버전·이행 정책이 설명되어 있고 다른 호스트에서도 같은 엔진을 사용할 수 있다.

WorkNaru·VS Code·MCP는 독립적인 사용 경험을 확장하는 연결 수단이다. 특정 통합의 존재를 제품 완성이나 agent-native의 필수 조건으로 삼지 않는다. DOCX 상호운용은 구체적 도입 수요에 따라 별도로 평가한다.

## 모든 단계에 적용할 품질 기준

안전성·입력 품질·접근성·성능은 마지막 단계에 몰아서 수행하지 않는다. 각 기능의 종단 흐름에 함께 포함한다.

- **원본과 호환성:** 독립 기대값으로 no-op·국소 변경·변환 손실을 검증하고 파일 문법/API 변경의 이행 영향을 설명한다.
- **사람의 경험:** 대상 OS·브라우저·입력기·키보드 탐색·오류 복구를 검증한다. 브라우저 자동 검증을 실제 사람/OS IME 검증으로 대체하지 않는다.
- **Agent의 경험:** 필요한 기능과 대상을 발견하고 실패를 복구할 수 있는지 실제 과제로 평가한다. 도구 수나 schema 유무만으로 효율을 주장하지 않는다.
- **규모와 성능:** 대표 문서 크기·객체 수·긴 편집 세션에서 입력 지연·메모리·저장 비용을 측정하고 지원 범위를 명시한다.
- **저장과 보안:** 초안·저장 원본·외부 변경을 구분하고 데이터 손실을 막는다. 문서·자산을 코드로 실행하지 않으며 renderer와 파일 접근 권한을 제한한다.
- **배포와 검증:** 설치·업그레이드·호환성 검증은 실제 사용 가능한 단위부터 수행한다. 코드·공통 계약·설명·예제·검증을 함께 갱신한다.

## 선행 관계와 작업 선택

선행 조건은 필요한 능력 단위로 판단한다. 다른 단계의 모든 기능이나 관련 없는 관리 작업이 끝나야만 다음 작업을 시작할 수 있다고 해석하지 않는다.

| 발전시키려는 능력 | 먼저 확인할 조건 |
| --- | --- |
| 문단을 넘는 자연스러운 편집 | 문서 단위 selection·gesture·history와 원본 매핑 책임 |
| 번호가 있는 그림·표·수식 참조 | 대상 식별, 번호 범위, 참조 해석의 공통 규칙 |
| 이미지를 포함한 문서 | 안전한 자산 해석과 이동성; 전체 Project 구현은 필수 아님 |
| Book 출판 | 구성 문서 해석, 장 순서, 통합 참조·번호·자산 정책 |
| 가져오기·이행 | 대상 모델의 표현 범위와 손실 보고·실패 보존 정책 |
| 외부 호스트 통합 | 재사용할 API·저장 경계와 독립 실행 검증 |

새 작업은 사용자가 겪는 제약, 필요한 선행 능력, 재사용할 기존 기능, 완료 후 관찰 가능한 결과로 설명한다. 가장 작은 유용한 종단 흐름을 선택하고, 관계없는 기반 정비나 미래 기능을 묶지 않는다.

## 선택적 확장과 비목표

Task list, 고급 서식, 병합 셀, 다양한 다이어그램 renderer, DOCX, Slides, 도메인별 requirement/traceability, 추가 호스트는 사용 수요와 유지 비용을 확인해 선택한다. 여기의 후보를 모두 구현해야 제품이 완성되는 것은 아니다.

실시간 협업/CRDT, 내장 AI 채팅, 범용 plugin platform, 모든 Markdown 방언의 완전 호환은 핵심 목표 달성의 선행 조건이 아니다. 기존 제품의 기능 수를 따라잡는 것을 성공 기준으로 삼지 않는다.

## 로드맵 변경 기준

사용자 문제와 검증 결과, SDoc 등 실제 사용 경험, 기술적 선행 관계가 바뀌면 로드맵을 재검토한다. 방향 변경의 이유와 대안은 관련 Issue/PR에 남기고, 중요한 기술 선택은 ADR 절차를 따른다.

개별 기능의 구현·병합·완료만으로 이 문서를 갱신하지 않는다. 장기 범위, 발전 순서, 선행 능력 또는 달성 기준이 바뀔 때 수정한다. 검증하지 않은 목표를 완료로 바꾸거나 현재 지원 문서의 사실을 로드맵으로 덮어쓰지 않는다.

기능 기획·우선순위 판단에는 관련 단계와 제품 원칙을 읽는다. 일반 버그 수정이나 국소 변경에 로드맵 전체를 의무적으로 주입하지 않는다. 읽기 경로와 작업 승인은 [AGENTS](../AGENTS.md)와 [기록 규약](project-records.md)을 따른다.
