# 0004. 협조적 lock·revision 기반 저장 유지

- 기록일: 2026-09-16
- Status: Proposed
- 과거 구현: 2026-09-16, [PR #4](https://github.com/NaruForge/narudoc/pull/4), 구현 commit `5c2f3a84c05a6b778c5b462f0945abb31cac1f21`, 보완 commit `07a94fb33167026a580a52416666eeeeeaf04ecc`
- 채택일: 없음 — 현재 유지 제안이며 과거 ADR 승인을 뜻하지 않는다.
- 검토 작업: [Issue #5](https://github.com/NaruForge/narudoc/issues/5)

## Context

자동화와 사람의 편집이 같은 파일을 다루므로 오래된 원본에 근거한 변경과 동시 쓰기를 식별해야 한다. 현재 파일 I/O는 CLI가 맡고 순수 문서 라이브러리는 파일 시스템에 의존하지 않는다. 실제 구현과 보장 한계는 [아키텍처](../architecture.md), 사용 계약은 [CLI](../cli.md)에 있다.

| 대안 | 현재 평가 |
| --- | --- |
| 파일을 바로 덮어쓰기 | 단순하지만 실패 중간 상태와 동시 변경을 방어하기 어렵다. |
| 임시 파일 교체만 사용 | 파일 내용 교체와 별개로 오래된 문서를 바탕으로 한 갱신 문제가 남는다. |
| 협조적 lock + revision 재검사 + 임시 파일 교체 | 현재 CLI끼리의 저장을 조정하고 확인 가능한 원본 변경을 거부한다. 비협조적 writer에 대한 완전한 경쟁 방지는 아니다. |
| 더 강한 OS·저장 서비스 기반 동시성 제어 | 다른 보장이 필요한 경우의 후보다. 플랫폼·배포·복구 계약을 새로 검토해야 한다. |

비교는 현재 유지 평가이며 과거의 미기록 판단을 소급한 것이 아니다.

## Decision

기존 문서 변경은 협조적 `.lock`, 원본 bytes의 SHA-256 revision과 파일 identity 재확인, 같은 디렉터리 임시 파일 및 rename을 사용하는 방식을 유지할 것을 제안한다. 읽기·편집 결과의 크기와 encoding 제약은 [파일 계약](../format.md)을 따른다.

- 실제 내용 변경은 lock을 얻은 뒤 원본을 재확인하고 임시 파일을 준비하며, 교체 직전 다시 확인한다.
- no-op 저장은 원본을 재확인하되 파일을 쓰거나 lock을 만들지 않는다.
- 신규 문서와 HTML 출력은 기존 대상을 덮어쓰지 않는 별도 생성 경로를 사용한다.
- 파일 입력은 symlink 경로와 hardlink 파일을 거부한다. 이 제한은 조회 명령의 파일 입력에도 적용된다.
- dry-run은 저장 경로를 실행하지 않는다. 잠금·저장 직전 원본·쓰기 가능 여부를 확인하지 않으므로 성공이 실제 저장을 보장하지 않는다.

`--revision`은 조회와 편집 사이의 원본 불일치를 검사할 수 있게 하지만 파일 시스템의 compare-and-swap이 아니다. lock을 자동으로 빼앗거나 삭제하지 않는다.

## Consequences

원본 변경·잠금 경합·잘못된 편집을 명시적 실패로 처리하고, no-op의 bytes와 mtime을 보존할 수 있다. 파일 I/O를 라이브러리 밖에 유지한다.

lock을 따르지 않는 writer는 마지막 검사와 rename 사이에도 쓸 수 있다. 완전한 CAS, 모든 외부 경합의 방지, 전원 장애 내구성을 보장하지 않는다. 비정상 종료는 lock이나 임시 파일을 남길 수 있으며 자동 삭제로 활성 writer와 경쟁하지 않는다. 실패 후 재시도는 원본과 진단을 다시 확인해야 한다.

다중 프로세스·호스트 협업, 다른 파일 시스템, 더 강한 장애 복구 요구가 실제 범위가 되면 재검토한다. 보장 강화는 단순히 설명을 바꾸는 것으로 달성되지 않으며 플랫폼별 실패·경합·복구 시험이 필요하다.
