# 0005. 순차 snapshot 기반 배치 편집과 단일 저장

- 기록일: 2026-09-16
- Status: Proposed
- 관련 작업: [Issue #9](https://github.com/NaruForge/narudoc/issues/9)
- 채택일: 없음 — 배치 기능 구현 승인을 ADR의 별도 채택으로 해석하지 않는다.

## Context

[실사용 검증](../authoring-scenario.md)에서 하나의 수정 요청을 개별 명령으로 저장하면 마지막 실패 시 앞선 변경이 남는다. 단일 문서의 기존 의미 편집을 묶어 사전 검증하고 최종 결과만 저장해야 한다. 원문을 재직렬화하지 않는 엔진과 CLI 파일 저장의 경계는 유지해야 한다.

대안은 (1) 개별 CLI 호출 후 실패 시 역편집, (2) 최초 snapshot에 대한 raw patch 목록, (3) 순차 메모리 snapshot을 검증한 후 단일 저장이다. 역편집은 이미 공개된 부분 상태와 외부 편집을 안전하게 되돌리기 어렵다. 최초 snapshot patch는 범위 충돌과 앞서 삽입한 대상의 후속 편집을 별도로 해결해야 한다.

## Decision

이번 구현의 순차 snapshot 방식을 유지할 것을 제안한다. 순수 Core의 `planBatch`는 버전 있는 요청을 검사하고 기존 `planOperation`을 순서대로 호출한다. 초기 문서와 각 단계가 유효해야 한다. 앞 단계의 결과를 다음 단계의 대상으로 삼고, edits는 단계별로 구분한다. CLI는 원본 revision을 필수로 받으며 최종 결과 크기를 확인한 뒤 기존 저장 함수를 한 번 호출한다. 상세 필드·오류·한도는 [CLI 계약](../cli.md)이 소유한다.

중간 invalid 문서를 허용하고 마지막만 검증하는 대안도 있지만, 기존 operation 의미를 바꾸며 손상된 구조의 대상 선택을 추가로 정의해야 한다. 이번에는 기존 의미와 검증 규칙을 재사용한다. 여러 파일과 더 강한 저장 transaction은 포함하지 않는다.

## Consequences

마지막 작업의 대상 오류나 검증 실패가 앞선 변경을 디스크에 남기지 않는다. 앞서 만든 대상을 다음 단계에서 사용하고, 전체 변경 상쇄를 no-op으로 처리할 수 있다. I/O·잠금·hash는 CLI에 남는다. 원문 slice·국소 patch 방식은 동일하다.

각 단계 재파싱 비용이 발생하며 한 요청은 100개 작업으로 제한한다. 단계별 edits는 독립적인 최초 snapshot patch가 아니므로 소비자가 순서대로 해석해야 한다. 실패 진단의 범위도 중간 snapshot 기준이다. 참조를 일시적으로 깨뜨렸다가 복구하는 편집은 지원하지 않는다. 저장 성공 여부와 내구성은 [ADR 0004](0004-file-save-guarantees.md)의 기존 한계에 따른다.

실제 대형 문서의 성능 요구, 중간 invalid 상태가 필요한 참조 재작성, 다중 파일 저장, 외부 저장 서비스가 필요해지면 재검토한다. 문서화나 PR 병합만으로 이 ADR을 Accepted로 전환하지 않는다.
