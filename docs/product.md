# NaruDoc 제품 비전

NaruDoc은 사람이 읽을 수 있는 문서 파일을 중심으로 사람·AI 에이전트·자동화가 함께 사용하는 구조화 문서 엔진이다. 사람에게는 편리한 시각적 편집 경험을, AI와 자동화에는 화면 없이 문서를 다루는 기능을 제공하는 것이 장기 목표다. 모든 경로는 같은 원본과 같은 문서 규칙을 사용한다.

이 문서는 제품의 목적과 지속적으로 지킬 성질의 원본이다. 현재 구현은 [아키텍처](architecture.md), 지원 문법은 [파일 계약](format.md), 실행 방법은 [CLI 계약](cli.md)에서 설명한다. 아래 장기 목표는 현재 기능을 모두 제공한다는 뜻이 아니다.

## 출발점

기존 SDoc에서는 작은 문장 변경에도 JSON 구조와 재직렬화의 차이가 섞여 Git에서 실제 내용을 검토하기 어려웠다. 편집기 중심으로 만든 구조에 CLI를 추가하면서 AI가 문서를 다룰 때 편집기 실행 환경과 상태가 장벽이 되었다. 특정 편집기의 내부 모델과 저장 형식이 연결되면 다른 편집기나 호스트로 옮기는 비용도 커진다.

NaruDoc은 사람이 직접 이해할 수 있는 원본 파일과 독립적인 문서 엔진에서 출발한다. 편집기와 뷰어는 그 엔진을 사용하는 client다. 문서 자산의 수명은 특정 편집기나 서비스의 수명에 종속되지 않아야 한다.

## 누구를 위한 제품인가

| 사용자 | 해결하려는 일 |
| --- | --- |
| 기술 문서 작성자 | 설계서·요구사항·시스템 설명서를 읽고 편집하며 문서 구조와 참조를 유지한다. |
| 개발자·검토자 | 문서를 코드와 함께 Git으로 관리하고 변경 이유와 영향을 검토한다. |
| AI 에이전트 | 문서 구조를 조회하고 지정한 부분을 수정한 뒤 검증 결과와 diff를 확인한다. |
| 자동화·CI 운영자 | 대화형 입력 없이 문서를 검사하고 결과물을 생성하며 실패를 판단한다. |

장기적으로 제목·문단뿐 아니라 표·그림·수식·요구사항·상호 참조처럼 기술 문서에서 의미를 갖는 대상을 일관되게 다루고자 한다. 구체적인 객체별 기능과 지원 문법은 별도의 작업으로 정의한다.

## 완성된 사용 경험

사람은 CLI를 배우지 않아도 시각적 편집기로 문서를 작성하고 구조와 진단을 확인할 수 있어야 한다. 개발자는 같은 파일을 직접 읽고 CLI로 수정하며 Git에서 검토할 수 있어야 한다. AI는 구조 조회 → 변경 계획 → 사전 확인 → 편집 → 검증 → diff 확인의 과정을 화면 조작 없이 수행할 수 있어야 한다.

이 세 경로에서 문서 내용과 의미가 달라져서는 안 된다. GUI의 선택 표시나 창 배치 같은 화면 동작을 제외한 핵심 문서 작업은 headless 환경에서도 접근 가능해야 한다. 편집과 검증 규칙을 client마다 별도로 구현하지 않는다.

## 지켜야 할 제품 원칙

- **원본은 읽을 수 있는 파일이다.** 전용 앱의 내부 상태나 데이터베이스 없이도 내용을 이해하고 옮길 수 있어야 한다.
- **작은 내용 변경은 작은 원본 변경으로 남는다.** 변경하지 않은 공백·개행·표현을 불필요하게 다시 작성하지 않는다. 섹션 이동도 그 내부 원문을 보존해야 한다.
- **엔진은 GUI 없이 존재한다.** 시각적 편집의 편의를 위해 AI·자동화가 특정 화면이나 편집기 인스턴스를 필요로 하게 만들지 않는다.
- **사람과 기계는 같은 문서 규칙을 사용한다.** 편집 결과와 검증 기준은 접근 경로에 따라 달라지지 않아야 한다.
- **문서는 특정 편집기·호스트에 종속되지 않는다.** 독립 사용과 다른 제품 안에서의 사용이 가능하도록 하고, 통합 제품 없이도 문서 자산을 사용할 수 있어야 한다.
- **실패를 확인하고 원본을 보호할 수 있다.** 잘못된 대상이나 오래된 문서를 바탕으로 한 변경을 식별하고, AI와 자동화가 성공 여부를 판단할 수 있어야 한다. 실제 보장 범위를 과장하지 않는다.

새 기능은 문서 의미와 headless 사용·검증을 먼저 정의한 뒤 사람을 위한 조작 경험으로 연결한다. 제품 원칙을 바꾸려는 작업은 그 영향과 근거를 명시해 검토한다.

## 목표와 현재 범위

| 구분 | 내용 |
| --- | --- |
| 장기 핵심 목표 | 구조화 기술 문서, 읽을 수 있는 원본, Git 검토 가능성, AI·자동화의 headless 작업, 사람을 위한 시각적 편집, 공통 엔진과 검증 |
| 확장 후보 | PDF 등 추가 출력, VS Code·WorkNaru 등의 호스트 통합, MCP 등 추가 연결 방식, 기존 문서 가져오기. 우선순위·범위는 개별 검토한다. |
| 현재 MVP 1 · v0.0.1 | GUI 없는 조회, 제목·섹션·문단·generic directive 편집, 검증, HTML 출력. 지원 문법과 작업 제약은 현재 계약 문서를 따른다. |
| 현재 MVP 제외 | 시각적 편집기·Web App, PDF/DOCX, MCP, 실시간 협업, WorkNaru 통합, 기존 SDoc migration, npm registry 공개 배포 |

시각적 편집이 현재 범위 밖이라는 사실은 장기 목표에서 제외되었다는 뜻이 아니다. 반대로 확장 후보는 출시 약속이나 일정이 아니다. Generic directive의 보존·편집을 지원한다고 해서 요구사항·표·수식 등 모든 도메인 기능을 이미 구현한 것은 아니다.

제품 차원에서는 Word의 모든 기능 복제, 모든 Markdown 방언과 문서 형식의 완전 호환, 정교한 출판용 페이지 배치, 특정 호스트의 전용 기능이 되는 것을 목표로 삼지 않는다. AI 자동 집필과 대규모 실시간 협업은 현재 제품 방향을 이끄는 핵심 요구가 아니다. AI가 안정적으로 문서를 다룰 수 있는 기반을 우선한다.

## 성공을 판단하는 기준

| 기준 | 확인할 경험 |
| --- | --- |
| Headless 작업 | 화면 없이 지원하는 핵심 조회·편집·검증·출력 과정을 끝낼 수 있다. |
| 원본 보존 | 변경 없는 저장은 원본 bytes가 같고, 국소 수정은 무관한 원문을 바꾸지 않는다. |
| Git 검토 | 문장 수정과 섹션 이동의 실제 의미를 diff에서 확인할 수 있다. |
| 경로 간 일관성 | 향후 GUI와 CLI에서 같은 핵심 작업에 같은 의미와 검증 규칙을 적용한다. |
| 문서 자립성 | 전용 편집기 없이도 텍스트를 이해·수정·복구할 수 있고 특정 호스트 없이 엔진을 사용할 수 있다. |
| 자동화 신뢰성 | 변경 전 확인과 충돌·오류 처리가 가능하며 성공을 문서 유효성과 혼동하지 않는다. |

현재 MVP는 원본 보존과 headless 작업의 기반을 검증한다. GUI와의 동등성 등 아직 client가 없는 기준은 향후 해당 기능의 완료 조건으로 구체화한다. 개별 작업의 승인 범위와 검증 결과는 [Issue](https://github.com/NaruForge/narudoc/issues)에 기록하고 진행 상태는 [기록 규약](project-records.md)을 따른다.

현재 API와 문법은 실험 단계다. 안정성이나 지원 범위를 과장하지 않으며 개인·회사 자료를 예제나 테스트에 사용하지 않는다.
