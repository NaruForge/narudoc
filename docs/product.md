# NaruDoc 제품 비전

NaruDoc의 본체는 사람이 읽을 수 있는 `.narudoc` 원본 형식과 편집기에 독립적인 구조화 문서 엔진이다. CLI·API와 향후 시각적 편집기·뷰어는 같은 엔진의 client다. 사람에게는 편리한 WYSIWYG를, AI 에이전트·스크립트·CI에는 편집기 실행 없이 문서의 전체 핵심 작업을 수행하는 경로를 제공한다. 모든 경로는 같은 원본과 같은 문서 규칙을 사용한다.

이 문서는 제품의 목적과 지속적으로 지킬 성질의 원본이다. 현재 구현은 [아키텍처](architecture.md), 지원 문법은 [파일 계약](format.md), 실행 방법은 [CLI 계약](cli.md)에서 설명한다. 아래 장기 목표는 현재 기능을 모두 제공한다는 뜻이 아니다.

## 출발점

기존 SDoc에서는 작은 문장 변경에도 JSON 구조와 재직렬화의 차이가 섞여 Git에서 실제 내용을 검토하기 어려웠다. 편집기 중심으로 만든 구조에 CLI를 추가하면서 AI가 문서를 다룰 때 편집기 실행 환경과 상태가 장벽이 되었다. 특정 편집기의 내부 모델과 저장 형식이 연결되면 다른 편집기나 호스트로 옮기는 비용도 커진다.

NaruDoc은 사람이 직접 이해할 수 있는 원본 파일과 독립적인 문서 엔진에서 출발한다. 편집기와 뷰어는 그 엔진을 사용하는 client다. 문서 자산의 수명은 특정 편집기나 서비스의 수명에 종속되지 않아야 한다.

## 엔진과 클라이언트의 관계

**Headless-first는 엔진의 독립성, CLI-first는 그 독립성을 먼저 검증하는 개발 순서다.** CLI는 GUI의 보조 명령이나 임시 데모가 아니라 최초 reference client이며, 시각적 편집기가 완성되어도 유지하는 1급 인터페이스다. 지원하는 핵심 문서의 생성·조회·수정·검증·출력은 CLI/API로 끝낼 수 있어야 한다. CLI를 브라우저나 편집기 자동 실행을 감싼 wrapper로 만들지 않는다.

**CLI-first는 CLI-only가 아니다.** 사람은 문법이나 명령을 외우지 않고 좋은 시각적 편집 경험을 누릴 수 있어야 한다. GUI도 같은 엔진을 호출하되 CLI subprocess를 반드시 경유할 필요는 없다. 핵심 의미 편집을 GUI에만 구현하고 headless 대응을 나중에 붙이는 구조를 피한다. 커서 표시·창 배치처럼 문서 의미를 바꾸지 않는 화면 전용 동작까지 CLI에 복제하지는 않는다.

편집기 내부 모델은 화면 편집을 위한 표현이지 canonical source가 아니다. 특정 편집기·브라우저·VS Code·WorkNaru 또는 MCP가 없어도 엔진을 사용할 수 있어야 한다. 다만 이는 모든 통합이 이미 구현되었거나 호환성을 보장한다는 뜻이 아니다. 제품의 엔진은 모델·파싱·의미 편집·검증·렌더링을 포괄하는 계층이며, 단일 `packages/core` 패키지와 같은 말은 아니다. 현재 책임 분리는 [아키텍처](architecture.md)를 따른다.

## 누구를 위한 제품인가

| 사용자 | 해결하려는 일 |
| --- | --- |
| 기술 문서 작성자 | 설계서·요구사항·시스템 설명서를 읽고 편집하며 문서 구조와 참조를 유지한다. |
| 개발자·검토자 | 문서를 코드와 함께 Git으로 관리하고 변경 이유와 영향을 검토한다. |
| AI 에이전트 | 문서 구조를 조회하고 지정한 부분을 수정한 뒤 검증 결과와 diff를 확인한다. |
| 자동화·CI 운영자 | 대화형 입력 없이 문서를 검사하고 결과물을 생성하며 실패를 판단한다. |

장기적으로 제목·문단뿐 아니라 표·그림·수식·요구사항·상호 참조처럼 기술 문서에서 의미를 갖는 대상을 일관되게 다루고자 한다. 구체적인 객체별 기능과 지원 문법은 별도의 작업으로 정의한다.

## 완성된 사용 경험

| 경로 | 완성형에서 기대하는 경험 |
| --- | --- |
| 사람의 시각적 편집 | 문법·CLI를 배우지 않고 문서를 작성하고 구조·진단·수정안을 검토한다. 저장과 핵심 의미 편집은 공통 엔진을 사용한다. |
| 개발자·외부 AI 에이전트 | 같은 파일을 조회하고 변경을 계획한 뒤 CLI/API로 편집·검증·diff 확인을 수행한다. 내장 AI 채팅이나 GUI automation은 필수 조건이 아니다. |
| 스크립트·CI | 미리 승인된 작업과 권한 범위에서 비대화형 검증·편집·출력을 수행하고, 오류·충돌을 기계적으로 판단한다. 사람이 화면을 열거나 매 명령을 확인할 필요가 없다. |

사람이 수정안을 승인한 뒤 저장하는 흐름은 유용한 선택이지만 모든 사용자의 필수 절차는 아니다. 제품에서 사람 승인이 필요한지는 호출자·호스트의 권한과 업무 정책이 정한다. 엔진의 validation·revision 검사·dry-run은 기술적 검증이며 사람의 승인과 다른 개념이다. 비대화형 실행도 권한·문서 검증·충돌 처리를 우회하지 않는다. 현재 CLI에서 dry-run은 실제 저장 성공의 보장이 아니다.

이 구분은 저장소 자체의 개발·push·PR·게시 승인 규약을 변경하지 않는다. 그 규칙은 [프로젝트 기록 규약](project-records.md)이 소유한다. 현재 실행 가능한 예는 [CLI 계약](cli.md)과 [편집 시나리오](authoring-scenario.md)에서 확인한다.

## 지켜야 할 제품 원칙

- **원본은 읽을 수 있는 파일이다.** 전용 앱의 내부 상태나 데이터베이스 없이도 내용을 이해하고 옮길 수 있어야 한다.
- **원본 보존은 diff 선호가 아니라 저장 계약이다.** 일반 편집에서 no-op 저장은 byte-for-byte 동일해야 한다. 의미 편집은 대상과 필요한 문법 경계만 바꾸며, 무관한 공백·개행·주석·표현을 재직렬화하지 않는다. 섹션 이동도 내부 원문을 보존한다. 포맷 정규화·마이그레이션처럼 원문 표현 변경 자체가 목적이라면 별도 명시적 작업으로 범위와 영향을 드러내야 한다. 이 예외 설명은 해당 기능의 현재 지원을 뜻하지 않는다.
- **엔진은 GUI 없이 존재한다.** 시각적 편집의 편의를 위해 AI·자동화가 특정 화면이나 편집기 인스턴스를 필요로 하게 만들지 않는다.
- **사람과 기계는 같은 문서 규칙을 사용한다.** 편집 결과와 검증 기준은 접근 경로에 따라 달라지지 않아야 한다.
- **문서는 특정 편집기·호스트에 종속되지 않는다.** 독립 사용과 다른 제품 안에서의 사용이 가능하도록 하고, 통합 제품 없이도 문서 자산을 사용할 수 있어야 한다.
- **실패를 확인하고 원본을 보호할 수 있다.** 잘못된 대상이나 오래된 문서를 바탕으로 한 변경을 식별하고, AI와 자동화가 성공 여부를 판단할 수 있어야 한다. 실제 보장 범위를 과장하지 않는다.

새 핵심 문서 기능은 Engine → CLI/API의 headless 실행·검증 → GUI 연결 순서로 설계한다. CLI와 GUI의 편집·검증 규칙을 따로 구현하지 않는다. 제품 원칙을 바꾸려는 작업은 그 영향과 근거를 명시해 검토하며, 단순히 현재 구현이 그렇게 되어 있다는 이유로 원칙을 바꾸지 않는다.

## 목표와 현재 범위

| 구분 | 내용 |
| --- | --- |
| 장기 핵심 목표 | 구조화 기술 문서, 읽을 수 있는 원본, Git 검토 가능성, AI·자동화의 headless 작업, 사람을 위한 시각적 편집, 공통 엔진과 검증 |
| 확장 후보 | PDF 등 추가 출력, VS Code·WorkNaru 등의 호스트 통합, MCP 등 추가 연결 방식, 기존 문서 가져오기. 우선순위·범위는 개별 검토한다. |
| 현재 MVP 2 첫 단계 · v0.0.3 | Headless 조회, 제목·섹션·문단·generic directive·표 편집, 검증, HTML 출력 및 제한된 단일 파일 로컬 시각 편집·저장. 지원 문법과 작업 제약은 현재 계약 문서를 따른다. |
| 현재 MVP 제외 | 완성형 WYSIWYG·다중 문서 Web App, PDF/DOCX, MCP, 실시간 협업, WorkNaru 통합, 기존 SDoc migration, npm registry 공개 배포 |

제한된 시각 편집 adapter를 검증한 뒤 [로컬 파일 편집 client](local-editor.md)에 재사용한다. 완성형 편집기는 별도 범위다. 반대로 확장 후보는 출시 약속이나 일정이 아니다. Generic directive의 보존·편집을 지원한다고 해서 요구사항·표·수식 등 모든 도메인 기능을 이미 구현한 것은 아니다.

제품 차원에서는 Word의 모든 기능 복제, 모든 Markdown 방언과 문서 형식의 완전 호환, 정교한 출판용 페이지 배치, 특정 호스트의 전용 기능이 되는 것을 목표로 삼지 않는다. AI 자동 집필과 대규모 실시간 협업은 현재 제품 방향을 이끄는 핵심 요구가 아니다. AI가 안정적으로 문서를 다룰 수 있는 기반을 우선한다.

## 성공을 판단하는 기준

| 기준 | 확인할 경험 |
| --- | --- |
| Headless 작업 | 편집기·브라우저 없이 지원하는 핵심 생성·조회·편집·검증·출력 과정을 CLI/API로 끝낼 수 있다. |
| 원본 보존 | 변경 없는 저장은 원본 bytes가 같고, 국소 수정은 무관한 원문을 바꾸지 않는다. |
| Git 검토 | 문장 수정과 섹션 이동의 실제 의미를 diff에서 확인할 수 있다. |
| 경로 간 일관성 | 향후 GUI와 CLI에서 같은 핵심 작업에 같은 의미와 검증 규칙을 적용한다. |
| 문서 자립성 | 전용 편집기 없이도 텍스트를 이해·수정·복구할 수 있고 특정 호스트 없이 엔진을 사용할 수 있다. |
| 자동화 신뢰성 | 승인된 작업의 비대화형 실행과 충돌·오류 처리가 가능하며, 기술적 검증·저장 성공·사람의 승인을 구분한다. |

현재 MVP는 원본 보존과 headless 작업의 기반을 검증한다. GUI와의 동등성은 제한된 adapter의 지원 범위에서 먼저 검증하며 전체 기능으로 확대해 주장하지 않는다. 개별 작업의 승인 범위와 검증 결과는 [Issue](https://github.com/NaruForge/narudoc/issues)에 기록하고 진행 상태는 [기록 규약](project-records.md)을 따른다.

## 설계 제안 점검

제품 설명·기능 설계·Agent 지침을 검토할 때 아래 선택의 이유를 설명할 수 있는지 확인한다. 정해진 문장이나 키워드를 반복하는지로 이해도를 판단하지 않는다. 표에 등장하는 미래 기능은 설계 사례이지 현재 지원 목록이 아니다.

| 제안 또는 질문 | 원칙에 맞는 판단 |
| --- | --- |
| 편집기와 브라우저를 제거하면 문서 작업도 중단되는가? | 지원하는 핵심 생성·조회·수정·검증·출력은 CLI/API로 계속 가능해야 한다. |
| 표 셀 병합을 GUI에 먼저 넣고 CLI는 나중에 붙이는가? | 먼저 의미 operation과 headless 검증을 정의하고 GUI가 이를 사용한다. 표 기능의 현재 지원 여부는 별도다. |
| 문장 하나를 고치면서 전체 문서를 formatter로 다시 저장해도 되는가? | 일반 저장에서는 무관한 원문을 보존한다. 명시적으로 요청된 formatting은 별도 범위를 갖는 작업이다. |
| 승인된 CI 작업도 매 수정마다 사람이 확인해야 하는가? | 제품 엔진이 일률적으로 강제하지 않는다. 호출자의 권한·승인 정책을 따르며 검증·revision·실패 처리는 유지한다. |
| Engine-first이므로 좋은 시각적 편집기는 필요 없는가? | 아니다. 사람의 WYSIWYG와 기계의 headless 접근을 함께 달성하되 원본은 파일로 유지하고 의미 처리는 엔진이 담당한다. |
| 완성형을 설명하면서 PDF·다중 문서 참조·MCP를 현재 기능처럼 약속해도 되는가? | 현재 계약, 장기 목표, 확장 후보·새 제안을 구분하며 구현·출시 일정을 추정하지 않는다. |

Agent의 목적 이해를 재점검할 때는 저장소 지침을 새로 읽는 세션에서, 기존 대화 없이 완성형 사용 경험과 위 설계 선택의 이유를 질문한다. 확인 가능한 대상 commit·사용 도구/모델·실제로 읽은 문서·판단 결과를 해당 Issue/PR에 남긴다. 누락이 보이면 현재 작업 디렉터리와 override·세션의 지침 갱신 여부도 확인하되 원인으로 단정하지 않는다. 매 코드 수정마다 이 평가를 요구하지 않는다.

문서의 링크·문구 검사나 작성자의 자체 점검은 독립 Agent의 행동 검증과 다르다. 실제 새 세션 평가를 실행하지 않았다면 이해도 개선을 실증했다고 보고하지 않는다.

현재 API와 문법은 실험 단계다. 안정성이나 지원 범위를 과장하지 않으며 개인·회사 자료를 예제나 테스트에 사용하지 않는다.
